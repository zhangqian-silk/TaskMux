设计定位：面向高智能 Agent 的通用任务控制系统。
文档日期：2026-09-06。

Yui 保存工作事实，提供可靠的原子操作，并允许通过插件扩展能力。Operator 代表用户处理全局事务；每个 Task 的 Leader 对任务推进和交付负责。Agent Runtime、会话、连接和工具实现都可以更换，任务不依附于其中某一个运行实例。

本集合是一份目标设计规范，不表示所列接口已经在当前 Yui 版本发布。命令和类型用于约定职责及行为；实施时应根据当时源码确定具体名称、复用位置和存储布局。数据接口不要求一一对应数据库表。

核心约定

  • 决策归 Agent。 框架不预设任务分解、评审顺序、重试次数或完成方式。
  • 任务由 Leader 负责。 用户可以直接和 Leader 对话，Operator 可以代表用户干预，但不另设日常任务调度大脑。
  • 事实独立于运行时。 目标、配置、工作分配、结果及必要回执持久化；进程句柄、连接、终端和可重建投影不成为任务真相。
  • 能力可组合。 Task 不按 software、research 等领域分类。Project 提供知识和资源，插件提供具体能力。
  • 扩展不等于扩权。 Agent 可以实现 Task-local 插件，但仍使用已经获得授权的执行环境和资源。
  • 故障沿既有职责上交。 Worker／Reviewer 交 Leader；Leader 交 Operator；Operator 由用户处理。

使用范围

默认部署是一位用户、一个 Home、一个 Controller 和当前受支持的存储。插件化以清晰接口和生命周期为基础，不要求微服务化。受信任模块可同进程运行；需要隔离的可执行扩展使用明确授权的执行环境。

实施任务完成后，Yui 应保持完整可用。必要时可以暂时保留两份实现，由同一个入口选择；它们共同使用唯一的持久化事实，不启动两个 Controller 并行管理同一个 Home。

1. 设计定位与阅读方法

Yui 是面向高智能 Agent 的通用任务控制系统。Operator 代表用户处理全局操作和 Task 划分；每个 Task 的 Leader 对规划、执行与交付负责。系统保存必要事实、提供原子操作，并允许用插件补充和替换具体能力。

架构从三个互补视角表达：工作关系图说明谁围绕什么工作；逻辑分层图说明哪些职责承接决策和执行；模块映射表说明代码与记录由谁负责。分层展示不要求增加相同数量的服务、进程或插件包。

图中的 Task 是工作事实中心，不是一个运行进程，也不是 Operator 的全部作用域。Operator 还可以直接修改全局配置、管理项目和插件；它创建多个 Task 后，每个 Task 都有自己的 Leader 和同样的闭环。

4. 各层的职责与边界

4.1 Experience Plane：统一交互，不拥有任务策略

CLI、Web、API 和原生会话入口负责输入、展示、必要确认和操作调用。用户可以通过它们与 Agent 对话，也可以直接执行确定的管理命令。

自然语言请求交给 Operator 或 Leader。确定的 CLI／API 操作直接进入 Capability Plane，不必先调用模型。已有原生 Leader 会话也可直接使用，不要求全部消息穿过 Web 聊天界面。

Surface 的展示消费查询结果。重新连接和页面刷新不重新执行业务动作，面板卸载不删除工作事实。

4.2 Intelligence Plane：唯一制定工作方法的层

Operator 负责全局意图、Task 边界、配置和跨 Task 协调。Leader 负责单 Task 的目标理解、WorkItem 拆分、执行选择、Review、恢复和完成。Worker／Reviewer 承担其局部责任。

Role、模板和 Skill 提供可保存的职责配置及行为指导，不是权限来源。Lane／replicas 是同一 Assignment 的多路执行方式，不与 Leader、Worker、Reviewer 并列为新角色；是否使用、如何综合结果由 Leader 决定。

决策层是职责视角。实际模型计算发生在执行层承载的 Agent Runtime 中，不意味着在 Controller 中再实现一个智能决策引擎。

4.3 Capability Plane：稳定事实与原子操作入口

这一层回答“现在有什么事实、我能做哪些操作”。Task／WorkItem／Review 是对工作对象的操作，Context 是查询视图，Role 是配置操作，dispatch／inspect／stop 是执行管理入口，资源动作和插件管理同样从这里使用。

Yui Tools 是这些公开入口的总称。CLI 命令、类型明确的内建调用和 describe／call 桥可以使用同一套操作；不要求所有内部调用都经过字符串 RPC。Capability Registry 用于发现和选择扩展实现，不是另一个 Task Store。

查询直接读取事实；本地修改通过所属模块的事务；需要运行 Agent 或调用资源的动作进入 Execution Plane。系统检查权限、对象关联和必要副作用边界，尽量不把业务方法固定为调用前提。

4.4 Execution Plane：执行已声明的请求

这一层承载已经被用户或 Agent 请求的工作。准入只检查当前角色是否忙碌、资源和实现是否可用；Mailbox 投递已保存输入；采集路径保存结果和必要回执；Wake 提醒读取新事实。

Execution 通过 AgentEndpoint 使用不同 Agent。产品、协议和传输是内部接口分工，只组合实际支持的路径。资源工具负责自己的外部动作与实际环境，不要求所有 Task 都使用 Git 或工作目录。

执行层不选择下一 WorkItem，不因失败次数自动换模型，不解析 Review 后建立修复拓扑，也不从原生 Turn 结束推断 Task 完成。

4.5 Minimal Kernel：共同事实与执行基础

Kernel 提供稳定身份、授权上下文、事务与必要操作记录，以及唯一的实现实例宿主。工作记录的语义仍由 Task、Agent、Execution、Resource 等所属模块解释，Kernel 不把所有业务对象变成自己的逻辑。

纯读通常没有 Command；本地事务直接修改所属记录；具有外部效果的操作保留必要请求身份和回执。这样既不漏掉未决副作用，也不为每个读取动作建立多层日志。

4.6 Plugin Fabric：贯穿各层的实现机制

插件可以贡献展示、原子能力、具体 Agent／资源实现和只读上下文材料；Role 模板与 Skill 优先作为数据。每项动态注册归属于一个实例，停用时按实际使用边界撤销。

Global／Project／Task 表示配置范围和可见性，不构成三套运行时，也不增加资源权限。宿主只维护一份实例关系和生命周期；目录从当前启用配置与注册贡献生成。

本机制不要求复杂依赖求解、服务网格、统一 Workflow DSL 或前端插件操作系统。一个能力能直接用普通模块实现时，不为了满足图形结构额外拆包。

热重载更新的是实现，不是任务含义。generation 只标识调用或会话实际使用的实现，历史 Candidate 保存内容与来源即可，不决定旧代码的保留时间。更新进度、模板或插件不自动决定结果是否仍适用。

8. 实现依赖与装配

Kernel 不依赖具体 Agent、领域资源或 Task 工作方法。Task 模块依赖存储和授权端口；Context 读取公开查询接口；Execution 保存自己的 Turn 证据并经公开能力关联任务；Runtime 与资源插件不直接写 Task 私有表。

一个装配入口知道内建实现并将其注册到宿主。其他模块依赖公开接口，允许普通的类型明确调用，不要求网络化。Agent 调用 Yui Tools 形成工作闭环，但不意味着源代码的 import 依赖必须形成环。

架构无需增加 DomainBinding、固定任务领域枚举、多级角色插件作用域或额外恢复主管。实例与记录数量按实际工作需要产生，不按图中的方框数量产生。

职责、交互与任务生命周期

层次位置：Intelligence Plane，通过 Experience Plane 与用户交互，通过 Capability Plane 使用 Yui Tools。 实际模型由 Execution Plane 承载。这里定义负责人和决策权限，不定义另一个运行时或工作流引擎。

1. 用户与 Operator

用户拥有最终权威。Operator 是自然语言操作代理，可以在用户权限范围内管理 Project、Task、Role、Agent、插件和执行。它不是只能创建任务的低权限分发器，也不是必须替所有 Leader 持续排程的上层主管。

Operator 根据请求的耦合关系、独立结果和用户预期划分 Task。与当前 Task 相关的细节可以直接交给其 Leader；跨多个 Task 的安排由用户或 Operator 处理。跨 Task 建议使用普通消息和知识，不需要专门的任务提案状态机。

用户 ↔ Operator：全局安排、配置、任务边界
用户 ↔ Leader：目标细节、方案、执行与结果
Operator ↔ Leader：需求变动、跨任务信息、必要干预
Leader ↔ Worker / Reviewer：具体责任与反馈

2. Leader 的完整责任

每个 Task 有一个逻辑 Leader。Leader 对任务结果负责，可以直接完成工作，也可以创建 WorkItem、分配角色、启动多个执行、请求 Review 或调用资源动作。

唯一负责人是协调规则，不剥夺用户和 Operator 的直接操作权。用户或 Operator 进行明确干预时，使用相同原子入口并留下来源。Leader 读取变化后调整方案。框架不再额外运行一个隐藏 Agent 来决定谁应当重做。

同一个逻辑 Leader 可以更换模型、Agent 或 Session。逻辑身份与实际执行者分开，避免换会话时重建整个 Task。对一个 Role 的执行请求通常串行接收；多个 Role 的工作可以并行。

3. 从 Draft 开始协作

Task 创建后即可建立 Leader Role。首次进入对话时按需启动或恢复 Session，不要求每个 Draft 常驻进程。

Draft 中的 Leader 可以读取项目知识、对齐要求、修改 Brief、记录重要决定、设计 WorkItem、研究问题和运行授权的临时实验。这里的结果属于规划材料，允许保存为供后续引用的 Artifact；不会仅因为创建了文件而被视为正式交付。

正式执行请求使用 Task 的 delivery authority。Draft 本身没有这类权限。权限边界由 Yui 工具和实际环境共同实现；若用户选择宽权限本地 Agent，文档中的角色约定不能替代真实文件系统隔离。

4. Activation 的含义

Activation 表示用户或受权 Agent 允许任务开始正式交付。它记录当时的任务说明引用和执行配置，准备必要资源，并使 Task 进入 active。它不把方案变成不可变约束，也不使之后的每次需求修改都必须重新激活。

环境可以为空。仅进行资料整理的 Task 不需要为了符合框架模型创建 Git worktree。需要准备外部环境时，先准备，再在一次状态更新中采用；准备失败仍可继续讨论 Draft。

激活时不会把正在运行的 planning Turn 即时升权。由当前 planning Turn 发起的激活请求，可以记录在现有操作记录中并立即返回请求引用，在该 Turn 结束后采用；不让工具调用等待自身结束。

原生 Session 的环境和权限可安全续用时继续同一个会话。否则创建新 Session，由持久化 Context 承接。会话连续性是体验，不是高于权限和事实的硬要求。

5. 对话中的信息管理

用户直接向 Leader 提供的信息，若影响之后的工作，由 Leader 写入当前 Brief、Decision 或 WorkItem。临时提问、试探性方案和一般交流可以留在原生对话中。

Yui 不增加自动语义提取 Agent。也不要求每次回复前都持久化一段摘要。Leader 在需要依赖信息跨会话存在时保存它，并通过简短回复说明重要选择已记录。

若原生输入能被可靠观察，可以保留可见输入及来源；不能观察时，不推测、不伪造用户消息。持久化之前发生的会话丢失，可能需要查看原生历史或再次询问用户。

6. 工作完成与结果判断

WorkItem 是独立责任；Candidate 是一版结果；Review 是针对结果的意见。它们帮助 Leader 管理交付，不规定所有 Task 必须使用同一套对象链。

简单的 direct Task 可以由 Leader 提交完成说明和必要产物引用。需要独立验收的 WorkItem 则通过 Candidate 明确选择被接受的结果。框架检查引用和权限，不从 Reviewer 文本或测试退出码决定接受。

任务状态变化不等于物理取消所有外部活动。Leader 完成或取消任务时，应明确仍在运行的执行怎样处理。迟到结果仍按原 Turn 保存，不自动重新打开任务或启动新的工作。

7. 配置切换与干预

Role 保存当前希望使用的 Agent、指令、Skills、模型、权限选择等。更换 Role 配置通常作用于下一次执行。已有 WorkItem、结果和消息继续存在。

若 Operator 更换 Leader 的实际执行承载，需要让旧承载不再提交新的管理动作；旧执行已经产生的结果仍然可记录。撤销管理入口不代表物理进程已经停止，对相同资源的冲突执行应按实际环境处理。

这是授权与资源边界，不是要求创建复杂的领导者选举系统。单用户部署采用现有 Role／Session 绑定校验即可。

8. 故障责任

工具参数错误首先返回调用者。Worker 或 Reviewer 的执行无法继续时，事实进入 Task 并通知 Leader。Leader 本身无法继续或主动求助时，通过现有消息路径通知 Operator。

Operator 的问题由用户自行处理。系统不创建备用 Operator、恢复 Task、专用救援运行时或 Operator 自动修复循环。普通配置、检查和启停入口仍然是用户可用的工具。

通知说明事实，不附带框架预定的业务恢复计划。有限连接维护可以保证已提出的动作被准确观察，但不因此自动更换 Agent、重做工作或重新提交效果未知的输入。

事实、配置与持久化

层次位置：Capability Plane 的事实与读取模型，依托 Minimal Kernel 持久化。 Context 与 Surface 展示消费事实；执行层保存结果和必要回执。模块记录所有权见总体架构。

1. 保存什么的判断标准

持久化服务于接手工作，而不是复刻整个 Agent 运行环境。每个拟保存字段都应回答：更换 Agent 或 Session 后，接手者是否需要知道它，或者系统是否需要它来防止错误副作用？

信息 典型内容 保存原则
用户意图与任务认知 目标、要求、重要决定、当前关注点 保存当前状态及必要修改来源
责任与配置 Task Leader、WorkItem assignee、Role 当前配置 保存，可显式修改
工作成果 Turn 输出、Candidate、Artifact、Review 引用、验收 保存结果本身及必要来源
待处理输入 Message、InputRequest、尚未确认投递的请求 保存直到有明确处置
未决外部效果 是否提交、是否被接受、相关外部回执 保存，避免接手后重复执行
可重建运行信息 句柄、连接、终端显示、内存队列索引、当前活动投影 允许丢弃或重新采样

原生会话 ID 可以作为继续使用原生历史的线索保存，但原生会话不是唯一任务知识来源。详细工具日志按实际诊断需求保存，不默认进入每次 Context。

3. 可变状态与不可变事实

Brief 和 Role 当前配置是可变状态。Decision 保存重要选择及原因，变化时可明确替代先前决定。Turn 的最终输出和已经提交的 Candidate 是已发生事实，不能随当前配置改写。

记录 revision 只解决并发修改：调用方读到一版记录，写入时检查是否覆盖了别人修改。它不是业务新鲜度判断，也不是候选是否可接受的总开关。

可以为 Brief 保存必要审计历史，但不需要把全部系统做成事件溯源，也不需要独立的 Spec 服务、交付依据版本树或全局失效传播算法。

4. 结果适用性由 Leader 判断

Assignment 保存本次实际交代的目标、验收说明和上下文引用，使结果来源可解释。Candidate 关联来源执行与具体产物。它们是信息，不是自动失效规则。

Leader 更新 currentFocus，只是在说明当前进展。Leader 修改要求后，可以认为旧结果仍然有用、需要部分修复或完全重做。接受时记录其明确选择及必要说明即可。框架不因任一关联对象 revision 变化就撤销已验收结果。

引用的产物应指向具体内容、已知不可变版本或动作回执。普通可变 URL 可以作为参考资料，但不能被误称为已冻结的结果版本。固定产物是为了让讨论双方看到同一份东西，不意味着冻结未来方案。

模板在应用时形成 Role 配置；模板后续变化不静默重写已有 Role。需要继承全局默认值时，明确哪些字段仍继承，并在实际启动时解析成一份有效配置。启动后的 Session 保留实际使用配置的引用或快照，不能通过读取当前模板猜测过去发生了什么。

配置可以保存完整的 provider 扩展选项，但 Core 只理解自己确实需要的字段；不为所有模型参数建立通用枚举。密钥不写入快照，保存凭据引用或非敏感描述。

6. Runtime 信息何时仍需保留

运行时的内存结构可以丢弃，但已经开始的操作可能仍在外部进行。恢复时至少需要知道其目标、提交关联、可能的原生 Session／Turn 身份以及目前是否已得到确定结果。

有可靠证据时继续连接或读取原执行；没有证据时保留 unknown，让 Leader 或 Operator 判断。不能因为本地进程不见了就假设输入没有执行。

与此相对，当前 CPU、token 速率、上次屏幕内容和一个可以重建的状态索引，不需要成为任务继续运行的条件。

8. Message、Wake 与消费

Message 保存发送方、接收方、Task、正文或引用及时间。Wake 只是提醒有新事实。它可以重发、合并或丢失后重新产生，不作为业务事实来源。

必要的投递记录关联一组消息与一次执行输入。只有实际接受证据成立时才记录送达；Context read 不隐含 ack，送达也不代表 Agent 已经把要求落实。要求是否落实体现在后续 Brief、工作和结果中。

目标角色忙碌时保留输入，不为了投递一条提醒再启动竞争会话。未知投递不因为更换了 Leader 就自动再发一遍。

9. 保留与清理

结果保留与执行环境保留是两个策略。历史 Candidate 需要结果内容和必要来源，不要求对应插件和依赖包永远可执行。插件代码由活跃调用、活跃或明确计划续用的 Session、未决操作以及用户显式保留决定。

临时文件和未采用环境可以清理；清理不得删除仍被工作结果引用的内容，也不能对仍可能存在写入者的资源作破坏性处理。具体资源采用自己的清理能力，Core 不建立万能垃圾回收工作流。

归档后的 Task、Brief、Decision、Turn 原始结果、Candidate、Review 引用、完成或取消说明及未决效果的最终处置仍经普通查询读取。清理工作目录前先保证引用内容可独立读取；“可恢复读取”不意味着恢复旧进程或允许 archived 回到 active。

10. 持久化契约

采用一个权威存储路径。纯读直接查询；本地修改用事务和必要版本检查；跨外部系统的副作用保存最小操作记录与回执。每次调用不必都生成多层事件、命令和日志副本。

执行、连接与实现替换

层次位置：Execution Plane；通过 Capability Plane 提供执行管理入口，并由 Plugin Fabric 支持实现替换。 角色行为属于决策层，模型及工具的实际运行发生在本层。

1. Execution 的外部模型

Agent 选择某个 Role 执行明确的工作，Yui 创建相应 Turn 并负责把输入交给配置的 Agent。上层获得执行引用、必要状态和结果，不必理解通信协议。

Turn 记录一次执行的目标、输入、Role、实际配置、关联身份、结果与错误。Session 是可复用的会话；Host 是持有连接或进程的实现。Task 不是其中任一对象的子生命周期。

Execution 只执行已经提出的请求。它可以因为同一 Role 正忙或资源容量不足暂缓启动，但不自己选择别的 Worker、模型或方案。

2. AgentEndpoint

统一入口保持少而明确：

inspect
cancel
steer（可选）
events
detach

detach 只结束 Yui 自己的连接或附件，不默认取消远端执行或销毁原生会话。取消和停止是显式操作，区分已经请求停止与确认停止。

能力描述只表达系统确实需要区别处理的事项：能否恢复原会话、能否可靠关联输入、是否支持运行中 steer、能否取消、是否可提供终端。未知能力明确未知，不根据 Agent 名称猜测。

4. 提交与返回

一次输入可能得到：明确接受、仍在等待、明确未产生效果、结果未知。通信写入成功不是对所有协议都等价的接受确认；晚到的、可准确关联的最终响应也可以提供接受和完成证据。

正常等待不能被统一超时策略判成业务失败。连接丢失之后，如果无法确认输入是否执行，保留原尝试身份并读取可得证据，不自动切换另一个实现重发。

PTY 提供人工可用的终端入口，但不因此自动具备结构化执行确认。不能把终端空闲图案当作某个 managed Turn 已完成的证明。

5. 多路与后台执行

多路执行共享一份明确 Assignment，记录副本与重试关联即可。Leader 决定参考哪些结果以及是否综合，不设置框架统一的成功数、投票或降级规则。

多路写入需要分离工作环境或由资源能力明确支持并行。支付、发送、发布等外部动作不因 replicas 参数被自动复制。原生 subagent 可以辅助当前执行，但不会自动进入 Yui WorkItem 图。

父 Turn 结束不一定代表所有后台活动都已经停止。只有需要继续使用可能冲突的资源时，才查看相关活动证据或采取停止／隔离操作；不把不相关的后台诊断变成整个 Task 的门禁。

这里的“热”只表示不必重启整个 Yui，不代表所有正在运行的对象必须即时采用新代码。

7. generation 的最小意义

generation 是实现实例的身份，用于说明某次调用实际落到哪份代码和配置。普通 Agent 不必手动管理它。宿主在选择实现时取得句柄，直到调用或 Session 不再使用后才释放。

新 Session 默认选择当前实现；同一旧 Session 的下一 Turn 通常继续原实现。需要换实现时，Leader 可以关闭或停用旧会话再创建新会话。通用透明状态迁移不是必要能力。

只需要固定会话实际持有的状态型依赖；无状态目录查询不必把整个系统依赖树冻结下来。动态注册的新工具可以经稳定的 Yui 调用入口在同一 Session 后续使用，而无需重载原生工具列表。

8. 插件启停

启用新实例时先完成验证与注册准备，然后一次发布完整能力集合。注册初始化不执行业务副作用。准备失败不影响当前可用实现。

普通停用阻止新的独立使用，既有调用或会话根据原句柄结束。权限撤回则立即影响新的受控副作用，两者不是同一个操作。无法撤回已经到达外部系统的动作时，记录实际情况，不宣称“卸载插件已经撤销操作”。

当没有实际使用者时，旧实例和代码可以释放。历史结果与来源元数据继续保留。存储迁移和不可兼容的内核更新走正常更新流程，不使用插件 drain 冒充数据库迁移。

9. 失败处理

Endpoint 如实提供证据。Worker／Reviewer 的失败由 Leader 处理；Leader 的失败由 Operator 处理；Operator 由用户处理。常规连接维护可以重连相同目标，但不自行改变任务策略。

能力、插件与资源

层次位置：Capability Plane、资源执行能力和横向 Plugin Fabric。 Agent 面向公开能力工作；具体工具和连接在执行层实现；Kernel 始终提供共同权限和实例宿主。

1. Capability 是 Agent 的操作模型

Agent 使用清楚命名的能力完成工作，例如读取任务、委派 WorkItem、查看结果、读取资源或激活插件。Capability 描述应足以让调用者知道输入、输出、作用对象和可能的副作用。

capability.search / describe / call
plugin.create / validate / activate / disable

名称是工具面，内部可以使用类型明确的函数或 Service。系统不要求所有内建方法都成为字符串调用，也不要求每项能力都有独立服务实例。

能力目录来源于当前配置和已加载实现，是可重建的读模型。Task 事实不依赖“某个插件现在一定在线”。调用时发现实现不可用，返回该事实，Leader 可以重新启用、换方法或补充实现。

2. 最小能力描述

一项能力至少描述名称、契约版本、输入输出约定、效果类别及实现身份。效果可简单区分查询、本地修改和外部操作。需要权限的资源由具体动作明确要求，不建立万能资源政策语言。

宿主从可信入口得到调用者身份；调用参数里的 taskId 只是目标，不能用 JSON 字段冒充 Operator。Task-local 插件不能覆盖核心管理命名空间。

如果可见范围里有多个同名实现，可以使用显式配置或由 Agent 选择。没有明确选择且无法唯一解析时返回歧义，不按加载顺序静默覆盖。一次调用选定一个实现，不在执行途中更换。

3. 插件与数据型扩展

                    |
             注册或应用贡献
                    |
     +--------------+------------------+
     |              |                  |

 Experience   Intelligence         Capability
                                        |

插件贡献可以跨层，但不会获得跨层改写事实的权限。每一项写操作仍由所属模块和共同授权入口处理。

可执行插件用于实现工具、Runtime 适配、资源操作或需要代码的贡献。Role 模板、Skill 和简单工具映射优先作为数据，由受信任解释器处理，不必为了“插件化”都变成可执行代码。

插件 manifest 保持小：id、version、apiVersion、entrypoint、provides、requires、permissions 和 reloadMode。只声明真实需要的依赖，不引入复杂优先级求解或多级 Bundle 工作流。

Scope 只有 Global、Project、Task。它决定配置归属和可见范围，不自动授予资源权限，也不是代码隔离机制。多个 Project 可以提供不同能力，同一个 Task 可以同时使用它们，不需要领域标签。

4. Project 与 Resource

Project 是长期工作背景：名称、说明、知识、资源引用和默认能力配置。Project 不等于 Git 仓库，也不承担任务排程。

Resource 的通用部分只有稳定身份、类型和必要元数据。具体能力由插件提供，例如 git.diff、document.read、browser.search。Core 不要求所有对象都实现相同的 read/write/execute/publish 接口。

Task 引用 Project 不等于获得 Project 的全部凭据。实际访问还需要相应授权。资源插件负责解释版本、外部句柄和操作回执，Yui 负责保留这些结果与所属任务的关系。

5. 环境与产物

Environment 描述一次执行实际使用的目录、挂载、网络、凭据和限制。它可以是普通本地目录、受限临时环境、已有容器或远程服务，也可以对无文件需求的任务为空。

环境不必成为 Task 的强制一等工作区。只有存在资源使用和清理责任时才记录环境归属。角色不因为拥有一段提示就获得文件系统写权限。

Artifact 是可引用的工作成果。内容文件可以保存摘要或独立副本；外部成果可以引用明确版本；已经执行的动作可以引用回执。Core 保留基本信息和引用，不理解报告格式或 Git 结构。

6. Agent 自扩展

Leader 在原任务中发现能力不足时，先判断是否可以用已有工具直接完成。一次性脚本已经足够时，不要求建立插件。需要重复调用、复用或加入能力目录时才实现插件。

查找能力 → 选择复用／组合／编写
       → 编写实现与输入输出说明
       → 验证
       → Task-local 激活
       → 经稳定调用入口使用
       → 保存原任务的实际结果

编写插件不是另一个强制 Task 类型。Leader 可以自己做，也可以委派给 Worker；软件开发能力只是完成这项工作的工具。系统不自动把每次 validation failure 转成修复 WorkItem。

7. 验证与执行信任

验证涵盖可解析的 manifest、类型和契约、加载卸载、声明能力是否完整，以及所选执行环境下的测试。报告绑定实际测试的代码产物，源文件更改后需要重新验证对应产物。

构建和测试也会执行代码，应使用同样清楚的授权边界。Agent 生成的可执行代码不默认导入控制进程。优先使用已有的受限环境和受权工具入口；用户明确选择 trusted-local 时，说明它依赖对代码的信任，不声称仅靠 manifest 提供隔离。

没有合适隔离时，可以先使用声明式能力或已有受权工具完成任务。缺环境是能力事实，不是必须构建一个全新沙箱平台的理由；扩大权限或信任范围由用户／Operator 的授权约定决定。

8. 能力增加与权限增加分离

Task-local 插件可在已有授权范围内自动激活，不必每次再让用户确认同一权限。新增凭据、外部写入权限、全局替换或更高信任级别，则应提出明确请求。

插件经由 Yui 再调用其他能力时，仍使用原调用者的权限，不能把一个查询能力包装成任意写入能力。发生部分效果时，保留已经得到的回执；输出格式错误也不会使真实外部效果消失。

9. 同一会话使用新能力

Agent 启动时已有稳定的 Yui CLI 或 describe/call 桥。插件激活后，下一次目录查询可以发现新能力，后续调用直接使用。这个桥不属于 Agent 必须先自己安装的插件。

因此自扩展不依赖原生 Agent 支持即时修改工具 schema。Skill 提醒 Agent 在缺能力时查询目录，而不是要求每次插件更新都重启所有会话。

10. 能力沉淀

Task-local 实现可以在工作结束后作为源文件和验证材料保存。需要跨任务复用时，Operator 可以将其配置到 Project 或 Global。这是一次普通受权配置操作，不需要 promotion 状态机。

扩大可见范围不会自动扩大资源授权。其他 Task 仍按自己的权限调用。历史 Candidate 只引用实际结果，不决定插件代码应保留多久。

具体接口见Plugin 与 Capability 模块；环境和产物职责见Project 与 Resource 模块。

端到端工作逻辑

阅读视角：工作关系、逻辑层次和事实流的组合。 自然语言经过 Operator／Leader 决策，确定操作可直达 Capability Plane；结果进入持久化，再由 Context 支持下一步判断。

本文用完整工作过程说明模块怎样协作。过程中的 Agent 决定不是框架强制步骤；每条链都可以根据任务需要缩短或组合。

1. 从全局需求进入两个任务

用户向 Operator 描述两个目标。Operator 判断它们可以独立交付，调用 Task 创建能力，分别建立 Draft 和 Leader Role。两份 Task 都持久化目标和必要背景，不要求立即启动两个常驻会话。

用户进入 Task A，与 Leader A 细化方案；同时也可进入 Task B。Surface 根据 Task 路由到对应 Leader，没有“必须回 Operator 转述”的限制。跨任务资料使用共享 Project 知识或带来源的普通消息传递，不建立自动跨 Task DAG。

事实链： 用户请求 → Task／Brief → Leader Role。
运行链： 用户进入 → 按需 Session → planning Turn。
决定者： Operator 划 Task，Leader 划内部工作。

2. Draft 中持续对齐

Leader 读取当前 Brief，讨论后直接更新要求或方案。对重要取舍写 Decision；日常进度写 currentFocus。必要资料通过 Artifact 保存，可从 Context 展开读取。

用户同意开始后，Leader 或 Operator 提出 Activation。若由当前 planning Turn 发起，请求立即返回，Turn 完成后执行资源采用。正式 Session 能兼容续用就续用，不能则打开新会话读取同一 Task Context。

Activation 的记录说明开始时依据什么，不限制之后继续讨论。临时实验内容可以显式引用或复制到交付环境，但不会因目录存在就自动被采用。

3. Leader 直接完成一个小任务

任务只需要整理一份说明。Leader 使用已有能力读取材料、生成文件、保存结果，然后调用 Task 完成能力写入说明和产物引用。

不需要合成 Worker、WorkItem、Lane、Review 或 Git Integration 来满足统一流程。Task 完成由明确操作产生，原生 Turn 的结束只保存该次回复。展示层读取两者各自的事实。

4. 两个 WorkItem 并行

Leader 建立两个可以独立负责的 WorkItem，分别配置 Worker Role 并发出执行请求。Execution 检查角色是否忙碌及实际环境条件，创建 Turn 并调用 Endpoint。

Worker 输出分别保存到原 Turn，通知 Leader。Leader 可以请求 Candidate、直接读取产物、发送反馈或接受结果。若一个 Worker 失败，另一个正常执行不受影响；失败只成为当前 Task 的一条事实。

要求改变时，Leader决定哪些工作需要调整。框架不自动根据每个 Brief 修改取消所有 Turn，也不以所有候选拥有同一 revision 为完成前提。

5. 同一工作多个独立尝试

Leader 请求两个角色对相同 Assignment 独立研究。ExecutionGroup 仅关联副本和各次尝试。每个结果保留来源；失败后重试仍归同一副本，避免综合时把一次重试当成两个独立意见。

Leader 可自己综合，也可委派一个主执行读取明确选择的结果。不默认“必须两个成功才能继续”，也不默认重复发布或发送。涉及写入时，先使用隔离环境或只读任务形态。

6. 用户直接改变要求

用户在 Leader 原生会话中说明目标变化。Leader 判断该信息需要跨会话存在，调用 Brief 更新并必要时记录 Decision，然后通知相关 Worker。

协议能提供输入证据时，Execution 留下可见来源；协议不能观察时，Yui 依赖 Leader 的显式写入，不补造消息。若 Leader 在持久化前失去会话，Operator 可根据现有记录和用户重新对齐。

已保存结果继续可读。Leader可复用它、修复一部分或重新执行；这些判断不由 Framework 的“过期”标记替代。

7. 切换角色使用的 Agent

Leader 将一个 Worker 的当前配置从 Agent A 改为 Agent B。Role 的逻辑身份不变，WorkItem 和消息不重建。

旧 Turn 仍按原配置结束，或者由 Leader 明确取消。新执行使用新有效配置，必要时新建 Session 并读取 Assignment 与持久化结果。新的 Session 不必重现旧会话的全部 token 历史。

配置切换不删除旧结果，也不需要全局重载所有插件。

8. 在原 Task 中补齐能力

Leader 需要处理一种当前目录没有覆盖的数据格式。它先查询现有能力，确认简单组合不足，再在授权的临时环境里编写转换插件。

插件声明输入输出与权限，测试后获得与代码产物关联的报告。Task-local 激活将完整能力注册到同一目录。Leader 经已有 CLI 调用入口使用新工具并保存业务结果。

验证失败由 Leader 修改实现。所需权限不足则向 Operator／用户提出具体请求。不需要创建新的开发工作流，更不能在插件初始化时偷偷发送业务请求。

9. 更换运行中的实现

Operator 启用一个新的 Runtime 适配实现。宿主验证后将新 Session 的默认选择切过去。已有 Leader／Worker Session 继续持有旧实现和必要连接，正在进行的调用不会中途变函数。

任务需要使用新实现时，负责人可以在当前执行结束后重开 Session。旧实例无实际使用者后释放；Candidate 和历史报告照常读取，不要求加载旧 Runtime。

短工具则以单次调用为边界更新，不需要为一次格式转换保留整个 Session。

10. 故障、未知效果与上报

Worker 执行失败，结果带必要证据进入 Task；Leader选择等待、修复、再派发或亲自处理。Leader 承载失败，现有通知路径将事实交给 Operator。Operator 承载失败，由用户处理，不增加恢复 Agent。

如果一个外部动作可能已经发生，Yui 保存未知处置和原请求引用。Agent 可以查询外部状态或处理可确认的部分，但框架不为了“兜底”自动换一份实现执行同一动作。

正常长请求继续等待并显示等待事实，不因为短期无输出就自动重做。

11. 重启后的接手

Controller 重启后读取当前配置、待处理输入和未决操作，重建目录和读视图。可连接的原生 Session 可以继续观察；不可用的由负责人选择新 Session。

任务目标、角色、WorkItem、结果和决定依然存在。Context 给出紧凑工作集，允许按引用展开。不存在“必须恢复终端屏幕或完整插件内存才能读 Task”的前提。

这些过程的验证条件见验收场景。

Kernel：事实与执行边界

层次位置：Minimal Kernel；为各层和 Plugin Fabric 提供共同基础。 本模块拥有唯一存储与授权基础、操作事实机制和实例宿主。Plugin 模块使用该宿主管理贡献，不再建立第二套实例权威。

分层位置与完整工作关系见总体架构。

1. 定位

Kernel 为所有模块提供稳定基础，而不是实现任务业务。其范围是身份、存储事务、可信调用上下文、必要的外部操作记录，以及一个插件实例宿主。它不解释 Task 目标、Review 文本、领域资源或 Agent 的计划。

单用户单 Home 部署只需要一个实际写入协调者。进程锁、事务和当前 Controller 发现机制按现有实现复用，不引入分布式选主。

2. 公开端口

Store.read / transact
Identity.allocate / validate
Authority.authenticate / authorize
Operations.begin / record / inspect
Host.attach / acquire / release / detach

这些名称是职责示意。存储端口不暴露给任意作者插件；具体应用模块通过受权能力处理 Task 修改。类型中的 actor 是可信入口得到的上下文，不是插件自己提交的 JSON。

3. 三类操作

类别 执行方式 持久化要求
只读查询 有界读取并返回 通常不建立 Command
本地事实修改 事务、必要 revision 检查、来源记录 写入业务记录即可，不复制第二账本
跨进程／外部副作用 在发起前保存稳定请求引用，执行后保存处置 保留未知效果及外部回执

请求的幂等键由可信调用入口验证，去重范围至少包含调用主体、目标和具体能力。相同键携带不同输入不能被当作同一请求。重试一个读操作通常不同于重做一个邮件发送。

账本状态描述操作是否排队、执行或结束；效果证据描述已知没有效果、可能有效果或确认发生。执行失败不能推导效果为零。一个动作只完成部分时，保留已知子结果或原回执，不要求为此建立通用分布式事务平台。

4. 未知处置

当通信丢失而外部动作可能已发生时，保留操作引用和证据，返回 unknown。重复调用可以返回同一操作引用，但不能自动再次产生外部动作。

能查询外部状态时提供查询能力；不能查询时由 Leader／Operator 决定是否接受重复风险或采用其他方案。任何显式重做都应是可见的新决定和请求，不篡改旧记录来伪造未执行。

等待一个仍然连接正常的长操作属于 pending，不等于 unknown。最终准确关联的响应可以补齐已接受与结果信息。

5. 授权与身份

授权决定某个调用者能对哪个目标做什么。Task 模块定义角色关系，Kernel 验证可信上下文和目标范围。用户／Operator 的全局权限不由普通插件通过参数声明获得。

Role 实际承载更换时，旧承载的管理凭据应失效；它的原执行结果仍可通过可信采集路径写到原 Turn。历史回执写入与新的管理动作必须分开识别。

资源授权和配置快照也分开：保存过去用过的权限配置不代表未来仍有权限。受控外部动作在执行前检查当前授权；已经发生的外部效果无法靠撤销令牌消除。

6. 唯一实例宿主

Host 负责实例身份、生命周期和动态注册资源。插件模块负责选择包和构建贡献。二者共用同一个实例表述，不分别保存两套“当前活跃 Provider”权威。

注册的 listener、timer、route、进程连接和能力句柄都属于某个实例的 disposer。使用方 acquire 后得到稳定句柄，结束后 release。长期会话持有它实际使用的实现；短工具只持有到调用结束。

宿主不需要自己知道 Code Review 或 Git。其 drain 只意味着停止新的独立使用并等待已有引用结束，不是业务取消。

7. 存储及更新

业务模块在同一存储契约下定义自己的记录。Kernel 管理当前支持的 schema 和升级入口。普通打开存储不隐式执行复杂迁移；升级使用明确备份和采用步骤。

代码路由回退、数据库降级、恢复备份和撤销外部效果各有不同意义。文档和命令不能用同一个“rollback 成功”掩盖这些区别。

实现可以暂时有不同 Provider，但不能各维护一份 Task 状态或操作处置。系统不允许两个 Controller 各自认为自己拥有同一 Home 的执行权。

8. 失败责任与非职责

Kernel 记录可确定事实并返回可操作诊断。它可以完成事务重放、同目标查询和去重通知等机械动作，不自行安排业务重试、换模型或创建修复 WorkItem。

不建设 Operator 救援子系统。Operator 无法工作时，由用户使用普通操作入口和环境工具处理。

9. 验收要点

同一本地修改重复请求不产生重复记录；外部 unknown 不被自动重放；失败但有效果的记录可读；撤权不删除原结果；插件句柄 release 后 effects 被回收；读取不触发业务写入。对应场景为 S09、S10、S11、S12、S25、S34、S39。

Task：任务事实与交付责任

层次位置：Capability Plane。 本模块提供任务事实的查询与原子修改。记录经 Kernel 持久化，Context／Surface 消费查询结果，Execution 提供执行证据；Task 本身不运行决策模型。

分层位置与完整工作关系见总体架构。

1. 定位与数据边界

Task 模块保存用户目标和工作事实，暴露原子编辑及验收能力。它不运行模型、不选择工作顺序，也不假设所有结果都通过 Git 交付。

核心记录包括 Task、Brief、Decision、WorkItem、Candidate、Review 引用和验收／完成说明。Message 与 Role 通过公开接口关联；Turn 结果由 Execution 保存，Task 不复制一份相同结果正文。

Task → Brief / Decisions
     → WorkItems → Candidate → Artifact / Turn result
     → completion note
Review → Candidate + Reviewer Turn

2. Task 生命周期

生命周期是 draft、active、completed、cancelled、archived。它描述用户是否计划、执行、结束或归档该目标，不表达每种内部活动。

Draft 可以进行对话、编辑与授权的规划实验。Active 允许正式交付。Completed 表示受权负责人明确确认结果；Cancelled 表示明确停止追求该目标。历史内容仍然可读。

结束任务会停止新的自动派发，不证明旧进程已经停止。迟到结果保存到原 Turn，不自动重开 Task，也不把保存结果称为 Task 归档。

起点 允许的目标 条件
draft active、cancelled 显式激活并采用所需环境，或受权取消
active completed、cancelled 负责人确认交付，或受权停止追求目标
completed active、archived 显式重开，或独立获得归档授权且满足下述前置
cancelled active、archived 用户／Operator 显式恢复目标，或独立获得归档授权且满足下述前置
archived 无 不重开、不激活；重复归档仅返回既有事实

重开必须明确选择继续的工作和输入；历史 accepted、pending、unknown 投递均不自动重播。再次追求 archived 目标应创建新 Task 并显式引用已有结果，不篡改归档历史。受权 Leader 可重开 completed；cancelled 的恢复和归档需要用户／Operator 授权，不由结束状态推导新权限。

归档前置：相关执行已结清，有实际停止或隔离证据；WorkItem 结果已集成或明确放弃；未决 InputRequest、Integration、外部操作已有明确处置；受管理工作区干净且可安全移除。若无法确认写入者停止、结果独立保存或操作处置，则保留 completed／cancelled 并返回具体阻碍，由负责人决定下一步。不增加自动清理或恢复协议。

归档记录保留先前 completed／cancelled 的身份、时间、操作者和结束证据引用；它本身不删除 Task 或成果。清理只作用于明确拥有且已无写入者的执行资源，不能删除用户目录、共享 Provider 服务或仍被引用的结果。历史正文和必要来源通过普通查询继续读取，不依赖旧插件可执行，也不暗示 Git 已推送或合并。

这是目标契约。当前版本使用 retired 而非 cancelled，并有额外隔离证据；后续 T03 必须通过中央存储迁移保留有效历史与权限保护，不直接将枚举改名或删除字段。

3. Brief 编辑

Brief 内容保持通用自由文本。更新接口支持只修改指定字段，并附 expectedRevision；发生并发修改时返回当前版本与冲突字段，使 Agent 能重新读取后继续。

currentFocus 可以用于进度和下一步关注点。修改它与修改方案都不会自动撤销 Candidate 或 WorkItem acceptance。重要选择用 Decision 表达，Core 不做语义分类。

可以保存修改来源和必要历史，便于用户查看规划怎样形成。历史用于理解，不参与另一个调度状态机。

4. WorkItem

WorkItem 是 Leader 确认值得独立负责的一项工作，包含 objective、acceptance、可选依赖和 assignee。Requirements 较长时可保存在正文或引用材料，不必重复 Task 的全部字段。

状态为 open、accepted、retired。运行与等待由 Turn 或执行请求派生；一次失败不把责任本身永久标成 failed。

依赖用于 Leader 声明“这项工作需要那个结果”，不是让 scheduler 自主设计 DAG。执行准入根据已经声明的依赖检查是否有可用结果。若 Leader 调整策略，可以修改依赖并重新提交执行请求。退休不暗中把依赖转接到其他 WorkItem。

同一 WorkItem 的 ordinary 执行避免无意重复写入；需要多路时显式使用 group。WorkItem 的编辑不会在运行中偷偷改写已经发出的 Assignment。

5. Assignment 与执行快照

一次派发保存实际交代的目标、上下文、Role 配置引用和资源范围。该信息可以存在 Turn 的 input snapshot 中，不必建立独立服务或表。

Leader 修改当前 WorkItem 后，原执行快照仍是事实。它可以继续、停止或接受补充指令，由 Leader决定。框架不根据全部 revision 变化自动取消运行。

6. Candidate

Candidate 表示明确提交的一版结果。必要字段是所属 Task、可选 WorkItem、来源 Turn 或受权导入、简短说明及 Artifact 引用。提交后内容和来源不可变；新版本结果创建新 Candidate，而非覆盖已被讨论的版本。

Artifact 可以是原始 Turn 输出、文件、外部版本或动作回执。没有额外文件的工作也可以把明确的结果文本作为产物，不应因为缺 Git commit 而无法提交。

Candidate 不拥有运行时，也不决定代码保留。其来源保存 Agent、插件版本等可解释元数据即可，不要求完整旧依赖包永久存在。

7. 验收与 Review

Leader 选择 Candidate 并接受 WorkItem，可附说明和 Review 引用。Core 验证权限、引用属于同一目标以及记录可读，不解析结果质量。

Review 关联一个 Candidate 和实际 Reviewer Turn。Reviewer 的原始结果只存在 Turn；Review 不维护另一份 verdict 文字，也不自动 reject 或生成修复任务。

要求变化后，Leader 可以明确说明旧结果仍满足需求并继续使用。Framework 不需要交付版本失效传播。需要撤回接受时保留历史验收，当前 WorkItem 回到 open，但不会自动重做已经消费过结果的其他工作。

Task 级 direct 结果可以直接形成完成说明及引用，不强制创建一个假的 WorkItem 或 Candidate。用户明确要求独立 Review 等硬条件时，由相应显式要求和能力验证处理，不把它设为所有 Task 的默认门禁。

8. 原子能力

主要能力为 task.create/edit/activate/complete/cancel/reopen/archive、brief.read/update、decision.record、work.create/edit/retire/dispatch/accept、candidate.submit/read、review.request/read。具体 CLI 层次可以沿现有命令组织。

这些能力返回记录或操作引用，不在返回前等待整个任务闭环。派发和评审请求交给 Execution；结果由通知让 Leader 读取。

9. 验收要点

Draft 编辑可恢复；进度不触发结果失效；当前方案变化由 Leader判断；Review 不复制输出；direct Task 无额外流程也能完成；取消或重开不复活旧未知请求。对应场景为 S01、S02、S04、S05、S06、S07、S08、S13、S40。

Agent 与 Context：职责配置及工作视图

层次位置：Intelligence Plane 的配置支持，以及 Capability Plane 的角色、沟通与读取入口。 Agent 实际推理由 Execution 承载；本模块保存 Role／Message 等必要事实，Context 本身只读并组织这些事实。

分层位置与完整工作关系见总体架构。

1. 模块组成

本模块包含 Role 配置、Agent 配置选择、Role／Skill 数据应用、Context 读取、对话目标和角色消息。它把持久化事实呈现给 Agent，不提供另一个 workflow planner。

Role 的行为指引说明应该怎样使用工具；工具入口的实际授权另由 Kernel 和应用模块执行。提示里的“你是 Operator”本身不授予权限。

不影响执行控制的展示字段可即时更新。指令和 Skills 的生效也以实际 Runtime 能力为准，不能因为数据库已改就声称运行中的模型已经读到。

本地工具错误返回当前调用者。Worker／Reviewer 的执行失败和主动求助通知 Leader；Leader 承载不可用或主动求助通知 Operator。使用已有 Event／Message，不建立额外故障队列。

运行观察只描述证据。没有足够进度不自动定义成“Leader失败”；可以向界面呈现，让用户或 Operator 检查，不派隐藏监督 Agent。

9. 配置、上下文与热更新

Role／Skill 当前数据可改变，但实际执行使用的快照保留。新工具通过稳定能力桥在当前 Session 后续调用中发现，不需要 Context 模块强制重启会话。

Context 无权固定插件代码生命周期。读取一个历史来源时只展示元数据和结果引用；只有实际准备再次执行时才请求可运行 Provider。

Execution 与 Runtime：一次执行的可靠承载

层次位置：Execution Plane；在 Capability Plane 暴露派发、查看、停止等原子入口。 本模块执行已经提出的请求、采集结果；Runtime／Protocol／Transport 是内部接口分工，公开使用统一 AgentEndpoint。

分层位置与完整工作关系见总体架构。

1. 责任

Execution 接受已明确请求的工作，建立 Turn，取得可用 Endpoint，收集输出并保存。它不对输出质量做判断，也不因为失败次数自动更换执行策略。

Runtime 内部负责产品启动、协议交互和连接。上层只使用 AgentEndpoint，不直接解析 terminal 字符、Provider Hook 名字或 JSON 字段。

2. 执行对象

对象 保存内容 生命周期
执行请求 目标、Role、输入、请求者 等待准入或被明确处置
Turn 实际输入、配置、原生关联、输出／错误 一次执行事实
Session 引用 原生会话 ID、有效配置、实现引用、环境 可跨多个 Turn 续用
Host 连接、进程、事件订阅、实例句柄 临时运行对象，可重建
ExecutionGroup 相同 Assignment 的副本及尝试引用 关联执行，不拥有工作流状态

Session 元数据可以持久化，实际对象不保存。Host 退出不自动删除 Session，也不自动完成 Task。

3. 最小 Endpoint 契约

Endpoint 能打开或恢复会话、提交输入、检查事实、请求取消、可选 steer、读取事件并解除附件。每项操作的具体支持来自实际实现描述。

提交结果包含 accepted、pending、not-submitted 或 unknown。accepted 的证据可以来自 Provider 确认或准确关联的终态；只有通信写入时明确标记证据较弱。内部可以分配本地 execution ID，但不把它命名为 Provider 返回的原生 Turn ID。

事件入口必须能关联到原请求、Session 及相应实现。重复事件不重复创建结果；迟到事件写入原 Turn，不完成后继 Turn。

4. 产品、协议与载体组合

产品适配知道 binary、版本、认证配置和启动预设。协议适配知道 Session、Turn、事件和错误语义。载体知道打开与关闭何种连接。

Endpoint 工厂只允许已声明兼容的组合。具体 CLI 是否支持 ACP、哪个版本或 native 连接，应在实现时探测验证。协议公共代码可以复用，但不同能力不被填成相同布尔值来掩盖差异。

Codex 与其 App Server 适配可同包；通用 ACP 实现可供多个产品使用。一个只支持终端的 CLI 可以作为人工终端资源接入，不自动成为高保真 managed executor。

5. 准入与并行

已经提出的执行请求检查 Role 是否有 active Turn、配置是否可解析、所需环境是否可使用。暂时不可用返回事实或保留同一请求，避免创建重复工作。

同一 Role 普通输入串行处理。不同 Role 可并行。多路执行共享一份 Assignment，每个副本有自己的尝试编号，重试不变成新副本。

资源写冲突优先通过分离环境处理。Execution 不建立全能资源锁系统，具体插件负责其资源的条件；已有写入证据不能只因管理配置切换就忽略。

6. 输入与用户共存

用户可能直接使用原生会话。若它已忙，Yui 保留输入，不抢占或静默插入另一轮。运行中输入的语义必须明确是 native steer、排队下一轮还是不支持；不能用同一个函数名字把三者混为一谈。

Controller 重启后可以根据保存的原生身份检查当前状态。可以证实的结果写回一次；不能确认接受与否的请求保持 unknown，不以新 Session 自动重发。

7. 结果、取消与后台活动

原生终态结束相应 Turn 并保存原始可见结果。Task 层再由 Leader 使用结果。

取消分为 request 和 confirmation。请求成功不等于所有后代进程和外部服务已停止。Agent 需要重用冲突资源时，查询相关活动或更换独立环境；无关活动不阻止任务其他部分推进。

原生 subagent 的输出可作为父执行证据保留，必要时单独引用已得到的结果。它们不自动形成独立 WorkItem，也不因父执行结束而假定全部已取消。

8. 实现更新

普通调用固定到调用结束；长会话固定 Endpoint 与其必要状态型依赖。新 Session 选择新版本，旧 Session 通常继续旧版本。

若旧运行实例丢失而代码不再保留，准确报告不能按旧实现续用。负责人可以新建 Session 从 Task Context 接手，不因此宣称任务事实丢失，也不悄悄用不兼容 Provider 恢复原调用。

热更新不保证零间断，不要求动态迁移所有协议状态。最小正确行为是明确使用哪个实现，并让用户／Agent有能力在适当边界停启。

9. 观察与故障

runtime activity 与 task progress 分开。正常模型长调用可以没有频繁工具事件；token 增长也可能不代表任务有成果。Execution 保存观察，不由它制定失败阈值驱动业务重试。

连接层已有的有限同目标重连可保留。失败通知按 Role 路由：Worker／Reviewer 给 Leader；Leader 给 Operator。Operator 自身问题没有额外自动处理机制。

10. 验收要点

关注真实提交证据、pending／unknown、迟到事件、同 Session 配置、用户直接输入、资源停止证据、多路尝试关系及 hot reload。对应场景为 S09、S11、S12、S14、S21、S22、S23、S24、S25、S35。

Project 与 Resource：背景、环境和工作成果

层次位置：Capability Plane 与 Execution Plane。 项目知识、资源查询和产物读取是公开能力；环境准备与具体资源动作属于执行实现。必要归属和结果经 Kernel 保存，不增加 Task 领域类型。

分层位置与完整工作关系见总体架构。

1. Project 的最小职责

Project 保存持续工作的背景，而不是再建立一个任务平台。内容为稳定 ID、名称与说明、知识、资源引用及默认能力配置。一个 Task 可以引用零个、一个或多个 Project。

Project Knowledge 保存跨 Task 有用的信息。Task 内临时判断放在 Brief 或 Decision；是否值得沉淀由 Leader／Operator 选择，不自动把所有聊天写入长期知识。

Core 不定义 software、research、document 的 Task 分类。Git、浏览器、资料处理等能力可以同时用于一个 Task；Bundle 只帮助安装和配置。

2. Resource identity

Resource 的通用记录保存 ID、类型、展示名称和非敏感定位元数据。具体插件负责它的真实地址与版本语义。例如本地目录、仓库、文档或数据库连接各有不同要求。

不同别名可能指向同一实际对象。需要并行写保护的具体插件应规范化身份，不能只比较用户填写的字符串。无需为完全不同的资源设计一套万能锁语言。

资源默认动作来自对应能力，如 diff、查询或发布。是否读取、写入或产生外部副作用在能力描述中声明，但 Core 不要求所有资源都实现统一 CRUD。

3. 资源授权

Project 引用不等于 Resource grant。Role 说明或插件 manifest 也不提供实际访问权。执行入口根据调用者和目标解析已授权的资源。

凭据通过引用和运行环境传入，不写进 Brief、Candidate、日志或配置快照。插件配置需要地址等参数时，限制仍由实际环境执行，而不是认为一个 permissions 字符串已经隔离网络。

用户选择 trusted-local 时，可以使用现有本地环境，但界面应明确其访问假设。需要更强隔离的自动代码使用已经验证的环境；框架不为缺少某种环境自动创造权限。

4. Environment 准备与采用

Environment 描述实际执行的 cwd、文件、挂载、网络、凭据引用和隔离方式。它可以复用一个授权本地目录，也可以由插件创建临时 worktree 或沙箱。

需要创建资源时先 prepare，返回临时引用和准备结果，再由调用方采用到 Task／Turn。采用前重新确认相关目标、授权及资源配置仍适用。没有采用的临时资源可以清理。

准备成功但启动 Agent 失败，不说明环境不存在；采用成功的事实继续保留，Leader 决定重试启动或换方法。不能靠回滚 Task lifecycle 隐藏已实际创建的外部环境。

无环境需求时采用空计划合法，不要求每个 Task 都有目录。

5. Draft 与正式环境

规划可使用只读资源或临时 scratch。需要跑实验时由实际授权环境决定能做什么。规划所得文件可保存为 Artifact 并用于说明，不自动视为 delivery 工作区。

激活后，Leader 可以显式复用已保存材料或复制实验结果，不要求机械地重做同一探索。正式结果需有明确来源，而不是整个临时目录未经确认直接成为最终交付。

6. Artifact 与内容保存

Artifact
  id / displayName / mediaType?
  locator or contentRef
  optional digest / externalVersion / receiptRef
  provenance

可变外部链接标为参考资料，并附观察时间。需要对一版结果评审时，固定内容摘要、外部不可变版本或独立副本；完成动作则引用可核验回执。

Artifact 不是执行环境。历史报告可独立于生成它的进程和插件读取。删除临时目录之前，确保其结果已保存到稳定位置，或明确标记后续不可读，不能继续声称 Candidate 内容完整。

7. 具体软件能力

Git repository、worktree、ChangeSet、checks 和 integration 可以由资源插件实现。现有成熟机制无需抽象成新的领域状态机，只通过明确接口和结果引用供 Leader 调用。

检查失败、冲突或目标变化返回具体文件／版本和已有输出。Leader 决定修复、重新生成结果或改方案。Git 动作保护自己的实际写入条件，不将一次冲突自动升级成整个 Task 永久失败。

非软件 Task 使用同一 Task／Candidate 模型，成果可能是报告、数据文件或动作回执。它无需加载 Git 插件才能结束。

8. 占用、取消与清理

Role 配置改变和 Turn terminal 不是所有资源已停止写入的证明。只有进行冲突操作时才需要相关停止或隔离证据。可以直接使用独立资源绕开等待，不必全 Task 停住。

清理按资源所有权和引用执行。用户拥有的目录不因为 Task 结束被自动删除；共享原生服务不被当作某个 Turn 的子进程杀掉。具体插件知道哪些句柄和文件是它实际创建的。

9. 能力不可用时的数据读取

资源插件离线时，已保存的描述、报告和回执仍然可以读取。需要实时查询或再次写入时才返回 capability unavailable。Context 不因缺少 Git 或浏览器插件而拒绝显示 Task 的目标与结果。

10. 验收要点

无 Git Task、空环境、固定产物、参考链接标注、授权检查、显式实验材料采用、实际资源清理与历史结果独立读取。对应场景为 S04、S13、S23、S26、S27、S28、S29、S37。

Plugin 与 Capability：发现、实现和替换能力

层次位置：Capability Plane 与横向 Plugin Fabric。 本模块管理包、配置、能力描述和注册；唯一实例生命周期由 Kernel Host 提供。能力目录是可重建视图，注册贡献可以覆盖展示、上下文、工具和 Endpoint 等层次。

分层位置与完整工作关系见总体架构。

1. 外部接口

Agent 的基本操作是 search、describe、call。扩展操作是 create、validate、activate、disable，reload 或扩大作用域属于管理操作。

search 默认查询当前可见目录和明确配置的来源，不自动联网下载或执行任意包。发现名称只是第一步，调用前还需读取契约和当前可用 Provider。

2. Descriptor

CapabilityDescriptor 包含 name、contractVersion、input／output schema、effect、必要授权说明和 Provider 引用。实现必须声明自己实际提供的内容，不能仅列一个名字。

核心管理命名空间由可信内建实现提供。Task-local 代码可以贡献新能力，不能用同名注册覆盖 task.complete、权限管理或正在承载自身的 Endpoint。

Registry 记录可见 Provider 并可重建；持久化的根是启用配置和实现来源，不是再保存一份可独立写的“目录真相”。

3. 选择与调用

显式 Provider 选择优先；否则只有唯一兼容且可见实现时直接选择。Global／Project／Task 决定可见性和配置来源，不按加载顺序形成隐式覆盖。

调用入口校验 schema、身份、目标和所需授权。执行前取得确切 Provider 句柄；调用结束释放。无副作用查询不建完整操作账本，本地修改复用业务事务，外部操作按 Kernel 记录。

插件委派其他能力仍使用原调用者的授权。通过受权入口执行的每一步都有必要回执，父插件输出格式失败时仍能知道已完成部分。直接代码执行本身不提供无限权限，实际环境必须对应所选择的信任方式。

4. 包与实例

manifest 保存 id、version、apiVersion、entrypoint、provides、requires、permissions、reloadMode。包是代码或声明式内容；实例是某次 scope 和配置下的加载。

代码产物需要可明确定位。验证报告绑定被测试的实际内容摘要，激活时检查是否仍是同一份内容。版本号只是名字，不能代替内容一致性。

SDK 不强制搭建包市场或签名基础设施。它首先应使一个本地独立目录能够验证并注册，无需改 Yui 源码。

5. 声明式优先

Skill、Role 模板、简单映射和已有工具组合优先作为数据。能够由现有文件／脚本能力一次完成的工作，不一定需要插件。

需要可执行代码时，Agent 在被授权的开发环境写 source 和 tests，不能直接写当前安装目录或把未验证的模块 import 进 Controller。构建与测试同样受运行信任边界约束。

验证报告只证明已执行的测试及环境，不证明未来任意输入安全，也不授予新权限。

6. 激活与注册事务

激活先解析 manifest、依赖和可见性，建立临时实例及完整贡献集合。初始化只做注册准备，不执行业务发布、发送或数据修改。全部准备成功后发布目录变化。

失败释放候选实例的 effects，当前能力保持可用。系统无需为 source、build、stage 等每一步建立长期任务状态机；源码和报告本身已能表达开发进度。

Task-local 插件默认只在该 Task 使用。提升到 Project／Global 是受权配置操作，保留来源，不自动授权所有其他任务访问其资源。

7. 与 Runtime 的不同更新边界

一个新文档转换工具可以在当前 Agent Session 下一次桥调用中立即使用。一个新的 Endpoint 协议实现则通常作用于新 Session。两种更新不需要绑成“插件变化就重启所有会话”。

宿主在旧调用或 Session 结束前保留其实际使用的实现。普通 disable 阻止新独立调用；已有句柄按原承诺结束。撤回授权时，新的受控副作用立即受限制，不能因为持有旧 generation 就永久获得旧权限。

不要求通用 live handover。需要时通过关闭旧 Session、打开新 Session 和读取 Context 完成接手。

8. Agent 自扩展完整性

自扩展成功的标准不是 plugin loaded，而是原 Task 已经使用新能力取得有用结果。

Leader 可以在同一 Task 内反复修改和验证，不因为失败自动创建开发 Task。缺少授信或网络凭据时向 Operator／用户提出具体请求。Leader 本身不可用交 Operator；Operator 的问题由用户处理。

稳定的 Yui CLI 或能力桥在启动时就可用，不让 Agent 先安装元工具才能安装第一个插件。若 Runtime 只能在下一 Turn 使用新信息，明确采用下一 Turn，不虚构当前模型已经收到更新。

9. 代码与历史保留

活跃调用、活跃／明确计划续用的 Session、未决操作和用户固定引用决定哪些产物继续保留。历史 Candidate 只保存结果和来源，不默认固定所有旧依赖。

代码删除后历史仍可读；再次执行需要重新安装可用实现，这是能力请求而不是结果读取的前提。

10. 验收要点

能力契约和歧义、scope 不扩权、validation 产物匹配、初始化无业务效果、同 Session 动态调用新工具、普通停用与撤权、历史代码清理。对应场景为 S25、S28、S29、S30、S31、S32、S33、S34、S35、S37。

Surface：一致的用户与 Agent 操作入口

层次位置：Experience Plane。 用户输入可以路由给 Intelligence Plane 中的 Operator／Leader，也可以直接调用 Capability Plane。展示消费 Context／查询；写入通过原子操作，不产生独立 Task 状态。

分层位置与完整工作关系见总体架构。

1. 职责

Surface 负责展示、采集输入、确认操作、调用能力和订阅更新。它不拥有 Task workflow，也不自己解释哪个结果应该被接受。

CLI、Web 和 Agent 工具对同一操作使用相同应用入口。CLI 的可读输出和 JSON 输出是同一结果的两种表示；不在 Web 里实现另一套重试或完成逻辑。

2. 两个对话目标

全局入口对应 Operator，Task 页面或 task enter 对应该 Task 的 Leader。Draft 页面同样有聊天入口。对话路由不以是否已经有常驻 Session 为前提，必要时由 Execution 按配置创建。

用户可直接执行明确操作，不经过模型。原生会话入口也允许继续与 Leader 交流；Yui 对无法观察的输入不声称拥有完整历史。

3. Task 视图

默认展示目标、当前要求、Leader 当前关注点、工作责任、结果与待回答问题。运行细节在可展开区域，包括实际 Agent、Session、Turn、错误和活动观察。

页面应让用户清楚区分：任务事实、当前配置和某次执行实际配置。Role 已改用新模型但旧 Turn 仍在运行时，显示两者而不是把历史执行标签重写成新模型。

不显示框架生成的强制下一步。可以提供当前对象支持的操作，但行动选择属于用户／Agent。

4. 读取与订阅

视图来自 Context 或受权查询。更新通知只触发重新读取或拉取 delta，不把通知正文当成另一份可写状态。网络断线后从游标补读或重建快照。

核心 cursor 不覆盖实时观察。页面显示观察时间和不可用来源，而不是用缺失值填充“正常”。可选插件面板失败不影响核心 Task 说明和结果读取。

5. 操作反馈

修改返回实际保存的记录或 operationRef。排队、等待、未知处置、失败和成功各有明确文案，不用一个“执行失败”掩盖可能已发生的效果。

确认用于扩大权限、破坏性动作或用户要求的决定，不为每一个已授权原子操作再加一轮固定人工审批。Operator 的自然语言操作同样遵守现有授权边界。

6. 插件贡献

CLI 可以注册命令描述并映射到能力调用；Web 优先接收受控面板描述、链接和结果呈现，而不是默认在前端执行任意插件脚本。

命令和面板随实例生命周期注册／撤销。卸载面板不删除 Task 数据，隐藏一个能力不等于撤销资源权限。可执行 UI 扩展若确有需要，需要独立明确的信任方式，不作为基础实现前提。

7. Agent 工具入口

Agent 使用稳定的 Yui CLI 或 capability describe/call 桥。工具目录可按 Task 当前可见范围查询；不必在每次 Prompt 中放入所有插件参数。

文档和命令帮助来自同一能力描述，尽量避免手工维护两套目录。工具输出包含稳定引用和简明事实，长内容提供读取指针。

8. 故障呈现

Worker／Reviewer 问题在 Task 中可见；Leader 问题按既有消息路径进入 Operator；Operator 的问题由用户处理。Surface 提供普通查询和操作，不附带独立自动修复逻辑。

插件、Endpoint 不可用也应允许显示已有结果。用户不需要启动生成该结果的旧 Runtime 才能打开文件或阅读完成说明。

9. 验收要点

CLI/Web 同源、Draft 聊天路由、配置与有效执行显示、断线补读、插件视图卸载、未知效果文案和无隐藏恢复流程。对应场景为 S01、S15、S16、S17、S19、S20、S30、S36、S38。

接口与数据契约

使用方式

model.ts 定义模块之间最少需要共享的结构；examples.ts 展示配置切换、结果引用、调用和插件配置；capabilities.json 是设计级能力目录。

这些是目标接口，不是当前发布 SDK。接口展示哪些信息应有明确所有权，不要求建立相同名称的类、服务或数据库表。已有实现可通过无持久化双写的边界包装满足契约；实现并存的限制见 T00 实施基线。

TaskState 包含 draft／active／completed／cancelled／archived。archive 仅在 archived 时必需，引用先前结束事实；TypeScript 的可选字段不代替运行时关联校验。允许转换、归档前置和不可重开规则由 Task 模块 唯一定义。Turn 的 cancelled 与 Task 的 cancelled 不是同一事实。

设计边界

Task、Role、Turn 和 Candidate 是不同对象。Role 的当前配置可以更新，Session 和 Turn 记录实际使用的配置。Candidate 不引用一个可执行插件句柄；仅保留来源说明和结果引用。

revision 用于记录并发更新；它不具有自动判断业务过期的含义。接受操作不要求所有来源的 revision 与当前状态相同。

只读调用不需要持久化操作账本。外部操作需要 requestId 和可核对的处置。effect 与 outcome 分开，失败可以伴随已经发生的效果。

Endpoint 的本地 attemptId 与可选 nativeTurnId 分开。实现只能填入实际观察到的原生身份，不能用生成 UUID 冒充原生回执。

Plugin scope 仅有 global、project、task。Manifest 不能自行决定自己是受信任代码；运行信任由宿主根据实际授权和环境产生。

共享入口

能力目录使用名称、输入输出 schema、效果类型和 Provider 来源描述工具。核心模块内部可以使用 typed port；Surface 和外部 Agent 经同一可信入口认证，不在 capability input 中自带可生效的 actor 身份。

接口中的 TrustedCallContext 是宿主传入的对象。TypeScript 类型不构成安全机制，实际进程或协议入口必须验证身份与授权。

类型检查

在包根目录、有 TypeScript 编译器的环境中执行：

tsc --strict --noEmit --target ES2022 --module commonjs \
  contracts/model.ts contracts/examples.ts

类型检查只能确认声明和样例匹配。原生协议、存储迁移、权限、隔离和停止行为分别由验收场景验证。

实施路线

1. 交付目标

实施从当前 Yui 可用能力出发，逐项建立本手册定义的边界。目标不是移动目录或增加抽象数量，而是每个任务都交付一个完整、可验证且保持产品可用的结果。

同一迁移 Task 可以由一个 Leader 负责，再按真正独立的责任划分 WorkItem。本文列出的实现步骤是参考路径，Leader可以根据当时源码调整顺序，但应满足目标接口和验收条件。

2. Task 依赖

T00 实施基线
 └─ T01 基础宿主与操作事实
     └─ T02 能力入口
         ├─ T03 Task / Role / Context ── T06 Surface
         ├─ T04 AgentEndpoint ───────── T07 ACP
         └─ T05 Project / Resource

T03 + T04 + T05 ── T08 Draft Leader
T02 + T05 ──────── T09 Plugin SDK
T03 + T04 + T09 ── T10 原 Task 自扩展
T04 + T09 ──────── T11 热插拔

T10 的 Active Task 闭环不依赖 Draft；需要同时验证 Draft 自扩展时再加入 T08。不同任务可以并行规划，实现涉及共享接口时先明确接口负责人和最小契约，不让多个分支分别创造同一事实模型。

完整机器可读定义见 task-index.json。各 Task 卡片包含目标、依赖、责任边界和证据要求；对应技术方案描述接口、存储、实施路径和异常处理。

3. 保持正常使用

纯新增能力可以直接接入；能完整等价替换的实现可以一次切换；暂时不宜替换的实现允许保留两份代码。每次调用或 Session 只选择其中一份，不在动作未知时自动执行另一份。

允许并存的是实现，不是两套 Task、Role、Turn 或操作处置。使用一个 Controller 和一个权威 Store。Schema 更新走当前产品支持的显式升级契约，保留可验证备份，不假定任意旧 binary 能读新存储。

在 Yui 仓库中，阶段并存还须满足 T00 基线的准入与删除条件： 当前消费者确有需要、一个唯一写入者、明确采用后删除条件。它不授权旧 payload 双读、启发修复、unknown fallback 或泛化兼容层；没有现实需要时直接实施当前合同。

每个迁移 Task 合并后应完整可用；开发中的中间提交不要求全部可发布。旧路径删除不是每个 Task 的必要目标，也不要求预先拆成机械的引入／切换／删除三个任务。

4. 验收分层

契约测试在可丢弃环境中验证结构、权限入口、生命周期、重放和结果关联。产品路径验证确认真实 CLI／Runtime／资源能工作。不能使用 mock 输出声称真实 Agent 已通过。

对真实账户、付费额度、共享目录或外部写操作，先确认对应资源与授权边界。普通 Task 测试默认使用临时 Home、fixture 和受控资源，不接触正在使用的任务。

文档与 TypeScript 检查仅验证文档结构及类型关系。场景索引中的 planned 表示待实施验证，而不是已经运行成功。

5. 代码定位方式

实施时先按职责搜索当前源码：记录 Store、公开命令、Role 配置、实际启动和投递、结果归档、资源创建与清理。文件名只作为当时的定位结果，不写成跨版本必须存在的承诺。

开始改动前确认三件事：同一事实由谁写入；当前用户主路径走哪里；新入口如何共享既有事实。完成后记录实际修改位置及测试证据，供后续 Task 继续工作。

6. 里程碑

里程碑 Task 可用结果
基础边界可用 T00–T02 内建能力使用同一受权入口与实例宿主
日常工作解耦 T03–T06 Task 事实、Runtime、资源和 Surface 各守职责
交互与扩展验证 T07–T10 第三 Agent、Draft Leader、真实自扩展
实现可替换 T11 按调用／Session 边界热插拔

这些里程碑是验收视角，不是额外运行状态。

T00｜实施基线与模块契约

硬依赖：无。

交付目标

确认当前实现中每项事实和副作用的唯一归属，建立可重复的正常使用基线，并将七模块边界映射到实际代码。

完成状态： 一份可执行的代码职责地图、主路径基线和接口采用顺序；不改变用户运行行为。

责任范围

  • 识别 Task、Role、Turn、消息、资源和插件相关入口及真正的持久化位置。
  • 标出当前 Codex／Claude 启动、投递、取消、恢复和结果归档路径。
  • 列出必须继续工作的普通操作及可在隔离 Home 使用的验证材料。

可独立分工的工作

  1. 梳理记录所有权与读写链。
  2. 整理运行与资源生命周期。
  3. 建立主路径验证入口及兼容约束。

这些分工供 Leader 判断，不要求按步骤建立 WorkItem。紧密耦合的实现应由同一责任单元完成。

不在范围内

  • 不重写运行时、不改 Task 生命周期、不对用户正在使用的 Home 执行迁移。
  • 不把本设计的每个类型机械映射成新表。

完成证据

  • 职责地图中的每个关键记录有且只有一个权威写入入口。
  • 主路径至少覆盖 Operator、Task、Leader 和一个现有软件交付过程。
  • 真实账户和付费资源的测试边界单独说明。

验收场景：S39、S44。场景定义见统一验收说明。

实施入口

已落实到固定源码的 T00 实施基线与后继交接 及 验证记录 是 task-10 的具体交付。 它们不改变下列目标方案，也不将未来场景标为已执行。

详细技术方案定义接口、改动位置的定位方法、存储影响、兼容路径和具体验证。共同执行约束见实施路线。

T01｜基础宿主与操作事实

硬依赖：T00。

交付目标

在现有持久化和授权基础上建立一个实例宿主，并明确外部操作的请求、处置和回执。

完成状态： 插件或适配实现可注册、取得句柄和释放；本地事实及外部操作仍共享现有权威存储。

责任范围

  • 建立实例身份、effect disposer、短调用引用和长期 Session 引用。
  • 对外部动作使用稳定请求身份，保留 unknown 与部分成功。
  • 把认证后的调用上下文传给实现，不信任插件输入中的角色。

可独立分工的工作

  1. 实现宿主和确定性 effect 测试。
  2. 复用操作记录并验证去重与 unknown。
  3. 验证现有存储兼容和授权入口。

这些分工供 Leader 判断，不要求按步骤建立 WorkItem。紧密耦合的实现应由同一责任单元完成。

不在范围内

  • 不做全局插件市场、跨进程服务发现或分布式租约。
  • 不创建 Operator 自动恢复机制。

完成证据

3. 操作事实

只读直接执行受权查询。本地修改用同一事务提交业务记录及必要来源。外部动作在发出前保存请求身份；记录 effect 为 none／possible／confirmed，outcome 另保存成功、失败或取消。

相同 requestId、目标和输入重复调用，返回原记录或继续查询原处置。相同 requestId 配不同输入，返回明确冲突。unknown 不触发自动调用其他实现。

构造一个可控制的假外部服务，能够分别在发送前、接受后、效果发生后、回执返回前中断。测试端记录实际接收次数；Yui 端检查本地记录与真实次数对应。

重点证明：失败但已有效果仍保留回执；输出转换失败不能清零效果；正常 pending 不被自动重发；恢复后读到原操作而不是创建新操作。

新字段或操作索引通过当前支持的 migration 链增加。普通 Controller 启动不隐式猜测修复未知 schema。测试备份在隔离 Home，不能以可回退代码路径代替数据恢复验证。

若暂时只有一部分动作使用共用入口，保持旧入口为当前事实写入者，新的 adapter 调用它；不能同时写新旧两份处置。

7. 验收

S09／S34 验证未知与部分效果；S10 验证本地 CAS；S25 验证句柄切换；S45 验证撤权；S44 验证升级采用；S20 确认未新增任何 Operator 自动恢复机制。

新入口对可信边界的依赖与 T01 相同：Controller 及其装配代码可信， 第三方实现仅得到一次调用的 context、嵌套调用和 evidence locator 端口。 这不是同进程任意 JavaScript 的安全沙箱；不能向插件代码交出 Host、 Registry、Store、认证器、调用者凭据或完整 ingress dispatcher。

3. 调用与权限契约

Controller envelope 包含 taskId、已有 managed caller 凭据， 以及 search 的 query 或 describe/call 的 request。 caller 来自 CLI 的 resolveJobCaller；它不属于 capability input。 任何 input 中的 actor/caller 注入、未声明参数或跨 Task 目标均拒绝。 envelope 格式错误、参数组合错误及跨 Task 目标沿既有 CoreApplicationError/INVALID_PARAMS 边界返回可操作诊断，不降为泛化 INTERNAL_ERROR；原认证失败仍保持其独立错误语义。

调用示例（在已认证 managed Session 内；开发时使用本 checkout 的绝对 launcher）：

yui capability search task --task task-12
yui capability describe task.update --task task-12
yui capability call task.read --task task-12 --input '{"taskId":"task-12"}'
yui capability call task.update --task task-12 --request-id edit-1 --input '{"taskId":"task-12","patch":{"title":"新的标题"}}'

effectful call 必须携带 requestId。Job 将它交给原 Job 去重事务， 同一调用主体和 requestId 重入返回原记录，参数冲突仍由原 owner 拒绝。 Task 元数据修改保持原事务语义；requestId 不新建本地修改账本， 也不承诺跨请求去重，重复明确修改仍会产生原有 Event。 元数据能力直接提交结构化 patch，旧 CLI 仅负责解析 flags 后调用同一事务。 以 -- 开头的标题/描述、包含逗号的单个 tag 都是数据，不再经过 argv 重编码。

Registry 校验输入 snapshot、当前权限和效果上限之后才 acquire。 每个嵌套调用复用原 TrustedCallContext 并重新认证；子调用的效果不得超过 父调用，query 无法借下游 local-mutation 或 external-operation 写入。 父调用返回或抛错时等待已发起的子调用收敛到调用结果，再释放句柄； 保留的 invocation 不能在父调用结束后作为新的 ingress。 这不等待异步 Job 执行结束，只等待已发起的能力调用返回其原 Operation。

目录按已认证当前 Task 及它引用的 Project 过滤；Global/Project/Task scope 仅增加或减少可见候选，不授予权限。必要权限由受信任装配器检查。 未获权的 descriptor 不出现在 search 中；撤权后旧 context 也不能发起新动作。

扩展贡献不得使用核心 namespace，亦不得借用核心 Provider ID 替换目录。 没有隐式 scope 优先级；多个可用 Provider 或多个可用未指定版本返回 ambiguous， 可通过 --provider、--version 明确选择。结果记录实际 provider/generation 与 explicit/unique 选择来源。唯一可用兼容者可以选择；不可用候选仍保留诊断， 显式选择不可用 Provider 不会改选其他实现。目录只读 Host 当前可用性， 不 acquire 或存储第二份实例状态。required 只沿明确名称/契约版本检查 已授权依赖及其可用性；缺失、已 detach 或无可用依赖返回 unavailable， 循环不会无限递归。不下载、执行或求解版本组合。

4. 返回与效果证据

返回 kind 为 value、operation、unavailable、ambiguous、denied、 invalid 或 failed，携带 effect 和 operations。 operation 是已有操作的观察值，不表示业务成功；必须读取其中原 state/outcome。pending、running、unknown 和 confirmed runner 观察均保持原义， 不转换为 capability 成功，也不发出另一 Provider 请求。

外部实现必须通过 invocation.observe 或嵌套调用提供原 owner 的 operationRef。 包装器输出 schema 不匹配、输出无法 JSON 序列化、父包装器抛错时， 已经观察到的 effect、receiptRefs、partialResultRefs 仍出现在返回中； 实际回执仍由原 Job 持久化。已进入实现的 effectful 异常或坏输出保守累积 possible，已有 confirmed 不降级；历史 queued/none Job 的观察不能证明 包装器没有产生其他效果，原 operations[].effect 则保持精确原值。 没有 evidence 的 external-operation 不返回 value 成功。 observe 不是持久化 API，也不授予写原 Job 的权限。

schema 是明确的有界 JSON Schema 方言：type、properties、required、 additionalProperties、items、enum、const、anyOf、minLength、minItems。 未知 keyword 在注册时拒绝，不能静默声称完整 JSON Schema 支持。 输出采用实际 JSON 投影校验，避免序列化失败绕过效果返回边界。 NaN/Infinity、bigint、函数和 symbol 值明确拒绝，不让非有限数静默变为 null。

同一 Role 的普通执行避免重叠。已声明 WorkItem 依赖可以检查是否有当前可用结果。暂时没有资源时保留同一请求或返回事实，由 Leader调整，不自动选择另一个 Worker。

6. 取消与资源事实

停止请求不能直接清空所有使用信息。Agent 需要重新利用可能冲突的目录时，获取已停止或隔离的证据。对未知或仍在后台执行的资源保留引用，但不冻结无关 Task 工作。

Leader 换绑先影响新的管理动作，旧结果仍可归档。真正冲突的资源操作经当前 Resource 能力检查，不能只看数据库 Role 已变更。

7. 兼容选择

新 Endpoint 未覆盖某个真实路径时可以保留当前实现，并在创建 Session 时明确选择。一个正在进行的请求不会在两条路径之间迁移；现有 Session 可以继续其原实现。

暴露当前选择和实际有效配置，便于验证。只在能证明同等行为时删除旧代码，不要求同一个 Task 完成全部清理。

8. 验收

2. 协议与产品分工

PTY 可作为人工接口，但不是结构化提交失败后的自动兜底。Codex native 路径保持独立，不强制为了统一 ACP 丢失已具备能力。

5. 实施切入

T08 技术方案｜Draft Leader 与正式执行

硬依赖：T03、T04、T05。

任务定义：交付范围与证据。

1. Task 与 Session 解耦

Task 创建时建立逻辑 Leader 和 Brief，不强制启动进程。用户进入 Draft 或 Operator 明确请求讨论时，按当前 Role 配置创建／恢复 planning Session。

会话持久化仅保存必要关联和有效配置。Task 可在没有会话时被读取和编辑，Leader 从 Context 恢复规划，不依赖终端仍存在。

2. Planning 行为

向 Leader 提供 Draft 可用的 Task 原子工具、项目知识、角色配置和必要研究能力。编写重要要求或决定由 Leader 完成，不通过隐藏模型提取全部聊天。

规划可使用授权只读资源或 scratch 环境。已有本地权限很宽时如实描述信任范围；不能只靠 purpose=planning 就声称 OS 写入被禁止。

成果可以保存为规划 Artifact。Activation 不自动采用整个 scratch 目录；Leader 可以显式引用材料或把所选内容用于正式结果。

3. 激活请求

请求包含 Task、稳定 requestId、期望开始方式和必要资源配置。Activation 记录只说明当时采用的任务说明和环境，不建立后续所有结果的版本一致性门禁。

若 planning Turn 已结束且资源可准备，可以立即采用；若请求来自仍在运行的 planning Turn，则在现有操作记录中保存 afterPlanningTurn，并立即返回请求引用。不要让同步工具等自己所属 Turn 结束。

用户在等待中取消请求或取消 Task，采用时重新检查明确状态，不继续执行历史意图。相关授权或资源配置变化时重新读取，只有影响实际采用的变化才需要重新准备，不因普通进度备注要求重新规划整个任务。

4. 资源采用

调用 T05 prepare 得到临时环境，可以为空。准备完成后在受控事务里采用环境引用并将 Task 置 active。失败时 Task 保持可继续 Draft，释放能够确认未采用的临时资源。

采用成功后 Agent 启动失败，保存 active 与环境事实，通知负责人决定再启动或换配置，不回滚成虚假的“什么都没有发生”。

5. 会话延续

当前 native Session 支持所需 cwd、权限和配置变化且已确认安全边界时可继续。否则创建新 Session，发送当前持久化 Context 和明确 delivery 指引。

不要求所有协议具备透明 handover，也不为保留聊天而在当前 Turn 中热升权。逻辑 Leader 不变，用户仍在同一个 Task 对话目标下工作。

6. Surface 配合

Draft 页面始终提供 Leader 入口并显示 planning；激活后显示正式执行及实际环境。此展示不维护独立 lifecycle。使用 T06 现有 target 路由，不另建 Planner 页面和 Planner Role。

Operator 可以创建多个 Draft 后让用户分别进入各 Leader，也可以对明确任务直接创建并激活。规划不是所有任务必须经历很长的一段流程。

7. 验收

S01／S02：用户在 Draft 对齐并持久化，关闭会话后再次进入能继续。S27：无资源准备的任务可激活。S40：当前 Turn 发起延后请求即时返回，结束后采用；取消或改变实际资源条件能够被正确识别。

还需分别验证可续用与不兼容需新建两条 Session 路径，结果不自动成为 Candidate。真实协议未验证兼容时默认新会话，不把文字声明当作证据。

T09 技术方案｜插件开发工具与受权执行

硬依赖：T02、T05。

任务定义：交付范围与证据。

1. 最小开发面

提供 create、validate、activate、disable 四个入口。create 建立独立开发目录及 manifest／示例实现；Agent 可以使用已有文件和执行工具编写内容。构建产物、验证报告和源码是文件／记录，不需要 Source→Built→Staged 的长期业务状态机。

声明式模板直接由可信解释器处理。可执行插件使用明确授信的运行环境，不默认进入 Controller 进程。

2. Manifest 与产物

manifest 定义 id、版本、入口、能力、依赖、权限和 reloadMode。目录扫描阶段只解析数据，不 import 作者代码。能力描述必须可在执行作者初始化前校验名称、输入输出和所需权限。

验证实际代码／依赖产物并计算内容摘要。报告保存摘要、环境和执行了哪些测试。activate 重新检查内容是否一致及当前授权，不仅比较版本字符串。

构建命令和测试同样可能有副作用，使用与信任方式一致的环境。不能把安全检查建立在作者自己的 validate 函数先获得任意权限之上。

3. 运行方式

可信内建可以同进程；声明式由内建解释器执行；自动生成的代码优先在已配置的受限环境中运行，并通过受权工具访问资源。用户明确选择 trusted-local 时允许相应执行，但不声称具有未实现的隔离保证。

T05 提供环境选择与授权；T09 对实际使用的方式验证边界，不要求自建一个通用沙箱系统。如果只有声明式路径已经可用，应清楚交付该能力，可执行闭环仍需单独证据。

4. 初始化和注册

activate 先加载候选实例并建立完整贡献集合，在发布前检查依赖、名字冲突、契约和权限。初始化只能准备注册，不进行发送、发布或修改用户资料等业务动作。

发布是一项清楚的目录切换。失败释放候选 effects，不留下部分已注册命令。新实例不覆盖核心管理能力；Task scope 无权替换承载自身的 Runtime。

5. 调用安全

真实权限来自入口与资源 grant。插件参数不能指定更高 actor；嵌套能力调用保持同一身份。受控查询不能通过下游能力偷偷写入。

若插件直接运行在 trusted-local，文档要明确该边界不是强隔离。任务权限和 Scope 的逻辑检查仍有效，但无法据此承诺宿主文件绝对不可访问。

6. 验证集合

结构验证：manifest、入口、能力集合、schema 与 required dependencies。

生命周期验证：load、完整注册、调用、disable、effects 释放；初始化失败不破坏现有目录。

行为验证：合法输入、错误输入、部分效果后的输出校验失败；当前 grant 撤回后的下一次受控调用。

信任验证：开发、构建、测试和运行均不能超出其实际环境承诺。负向测试必须在所选真实隔离环境执行，不能以类型检查或 mock deny 替代。

7. 兼容与验收

现有内建插件可以先使用 trusted-builtin 路径，不强迫它们全部进入独立进程。外部 SDK 与稳定调用入口接入后，不需要修改 Yui 安装目录。

S28／S45 验证权限；S29 验证初始化；S31 验证报告与产物一致；S34 验证真实效果不被输出错误抹除。产物验证成功是加载条件，不是业务任务完成的条件。

T10 技术方案｜原 Task 中的 Agent 自扩展

硬依赖：T03、T04、T09。

任务定义：交付范围与证据。

1. 原任务闭环

自扩展是 Leader 完成原工作的一种方法，不是框架自动选择的流程。Leader发现 capability unavailable 后，判断已有工具、脚本或声明式组合是否足够，必要时再编写插件。

本任务交付必须包含一个真实原 Task 的结果：仅注册一个 hello 插件不算完成。

2. 稳定元工具

Session 启动时就提供 Yui CLI 或 describe／call 桥，以及 plugin.create／validate／activate。这个入口由可信内建提供，不能要求 Agent 先安装它才能安装第一个插件。

目录变化后，后续桥调用读取当前可见能力。原生工具 schema、系统提示和 Endpoint 不要求被热改。即使模型只在下一 Turn 得知新工具，也可以继续同一 Task，不重启整个 Controller。

3. 首个实现场景

使用授权的本地资料，任务需要把一份特殊 JSON 格式转换为报告。当前目录没有该转换能力。Leader 查询目录，选择实现小型解析／转换工具，写输入输出和测试，验证后在 Task scope 激活。

Leader 随后真实调用新能力，保存报告内容，形成 Candidate 或 direct 完成说明。测试中可放入一个格式边界，使 Leader 在验证失败后修复代码并继续，而不是由测试脚本替 Agent写最终实现。

声明式场景和可执行场景分别记录。可执行版本必须有 T09 对应运行信任证据，不以声明式成功替代。

4. Agent 行为指导

Role Skill 只规定复用优先、必要事实持久化、权限不足提出具体请求和不要修改核心安装目录。不规定每一步必须调用哪个工具、失败几次换模型等策略。

高智能 Leader 可以选择临时脚本完成一次性工作；不要为了统计自扩展次数强制把所有脚本注册。只有选择了插件路径时才验收注册与重复调用能力。

5. 权限与 scope

Task 已有授权足够时，验证和 Task-local 激活不再重复要求同样的人工批准。需要新的资源、网络、全局替换或信任级别时，由 Operator／用户处理。

Leader 不能通过新增插件覆盖核心管理能力，不能替换当前承载自己且尚未安全结束的 Endpoint。确有全局变更需要时发普通 Message 给 Operator，不创建特殊恢复工作流。

6. 失败与结果

语法错误、缺依赖、validation failure 作为事实返回，Leader 自己修复。插件部分完成外部动作时，Context 提供已有回执，不能修复后自动重跑整个动作链。

插件成功调用之后保存业务成果，不把 Plugin source 当成所有任务的唯一交付物。代码可以保留以便复用，历史结果读取不依赖它继续活跃。

7. Draft 与依赖

Active Task 首个闭环依赖 T03、T04、T09。Draft 的同类探索在 T08 可用后附加验证，不阻塞本 Task。验证时记录是否在同一 native Session、同一 Task 中继续，不能把新开完全独立任务的成功冒称原任务自扩展。

8. 验收

S32 证明原 Task 真实使用新能力；S33 证明验证失败能由 Leader 修复；S42 证明同 Session 通过稳定桥发现新工具；S28／S45 证明插件不扩权。

完成证据包括 Agent 实际操作记录、验证报告、激活来源、工具调用回执和业务产物。自扩展是否有价值以结果为准，不以框架新增多少对象为准。

T11 技术方案｜按使用边界热插拔

硬依赖：T04、T09。

任务定义：交付范围与证据。

1. 更新边界

热插拔的目标是更新能力而不停止整个 Yui。三种实际边界：无状态展示随注册生效；短工具在当前调用结束后换实现；Endpoint 默认按 Session 更换。存储和核心授权契约不纳入任意热替换。

用户选择 reload 时，返回实际采用方式和仍在使用旧实例的引用，不承诺所有运行中对象即时变成新版本。

2. 新实例准备

获取并验证新产物，建立候选实例和完整贡献集合。必要依赖、schema、权限和环境检查通过后发布新的选择。初始化不做业务副作用，失败撤销候选 effects，原实现仍服务当前工作。

一次 Registry 切换只影响新的 acquire。没有新工作选择到半初始化 Provider。版本名与代码摘要绑定，不能更新同一目录却继续声称旧 generation 内容不变。

3. 短调用

call 在开始时 acquire Provider，到结果与必要回执保存后 release。新实现可以在旧调用进行时注册，后续独立调用使用新实现。当前调用即使发生 unknown，也不能为了 drain 直接再执行新实现。

当操作结果未知且后续查询需要原实现时，保留必要产物；已有结果完全固定后，不因为历史 operationRef 存在而永久保留代码。

4. 长期 Session

Session 取得 Endpoint 和实际持有的状态型依赖。新 Turn 在同一 Session 默认仍使用这组实现。新 Session 使用当前 Provider，配置与来源分别记录。

不要求通用 live handover。负责人可以等待、显式取消或在适当时机新建 Session。Session 结束后旧实例引用归零即可清理；空闲但仍明确续用的 Session 可以继续持有。

只固定有状态依赖，不把能力目录、所有 Project 和历史结果连成永久锁。动态新增短工具依然通过稳定桥在旧 Session 后续调用可见。

5. 停用与撤权

普通 disable 停止新的独立使用，让已取得句柄结束。明确撤销授权则影响后续受控副作用，即便旧句柄仍存在。两者在界面和 API 中分开表达。

停止请求不等于进程已停止，drain 超时只返回仍在使用的事实，不自动升级成杀死共享服务。需要强制处理时由 Operator／用户作明确选择，并记录可能未决的外部效果。

6. 历史与清理

产物保留依据是活跃使用、未决操作、明确的续用意图或用户保留。Candidate 和 Review 保存结果及来源信息，不要求可执行代码永久存在。

清理后历史页面仍能读取报告和原输出。再次要求按旧实现执行时可以返回能力需要安装，而不是把历史结果标成损坏。

7. 实施验证

用可阻塞的工具实例 A 启动一次调用，再启用 B。证明 A 返回原结果、B 处理新调用，A 完全释放后才 dispose。模拟 B 注册失败，A 仍可用。

再用长期 Session A 启动及结束一个 Turn，启用 B 后在同一 Session 发下一 Turn，确认仍由 A 处理；新建 Session 使用 B。测试在旧 Session 内通过稳定桥调用一个新短工具，证明两种更新边界相互独立。

最后停止旧会话并清理代码，验证历史 Candidate 可读。撤回 grant 后旧句柄不能继续发新的受控副作用。

8. 验收

S14／S35 验证 Session 边界；S25 验证短调用；S42 验证新能力可见；S37 验证结果与代码保留独立；S45 验证授权时效。

这些必须包含实际实例计数与请求记录，不以“状态显示 draining”作为真实停止或清理完成的证据。

纯结构场景可用临时 Store、假 Endpoint 和受控外部服务执行；涉及真实 CLI、原生用户输入、实际权限与进程停止的场景，需要真实实现和明确授权环境。记录实际输入、结果引用、Provider 版本、外部效果证据和未覆盖范围。

通过一个 mock 拒绝不能证明宿主隔离有效；通过静态类型检查不能证明协议确认正确；界面显示 draining 不能证明进程停止。每个迁移 Task 应提交与其声称行为相称的证据。

预期： 路由到该 Task 的 Leader，按需启动 planning 承载；不要求先建立 delivery 环境或先激活。

预期： 新会话能读取已经确认的规划信息；不需要恢复旧终端或完整工具日志。

Yui Tools Agent 和确定性用户操作使用的同一套公开查询与原子能力

Operator 代表用户进行全局操作的 Agent，不是所有 Task 的固定日常调度者

固定与开放

固定的是身份、责任、当前事实的写入边界和必要操作证据。开放的是工作方法、具体工具、资源类型、运行协议以及结果内容。

文档中的类型名称用于共享理解，实施可以复用当前数据结构或存储，只要保持相同的可观察语义。

实现取舍原则

1. 先判断是否需要框架机制

能够由 Leader 根据现有事实判断的事项，优先提供信息和操作。需要跨会话接手、需要保护资源或需要确认外部效果的事项，才进入持久化和机械检查。

不要把“有一个分支可以自动处理”直接等同于“必须建立自动恢复策略”。一个清楚的错误、结果引用和可调用工具往往已足够。

2. 少量概念具有明确责任

普通模块、插件包、数据库记录和运行实例不是一一对应关系。一个 Plugin 可以包含产品和协议代码；一个 Turn 可以保存 Assignment 快照；一份操作记录可以表达整个受控动作及部分回执。

只有独立复用、替换或生命周期确实需要时才拆分。不要为每个 parser、每个 Hook 或每个领域名增加一级 Registry。

3. 查询不产生业务事实

Context、目录、UI 状态和资源观察可以重建。读取不表示已经落实要求，也不表示消息已接受。运行观察带时间，不伪装成任务当前真相。

4. 更新不改写过去

Role 配置更新、插件更新和 Brief 编辑影响之后的判断与执行。历史输入、输出、Candidate 和回执保持来源清楚。是否继续使用某结果由 Agent 决定，而不是统一 revision 比较。

5. 错误范围尽量局部

一个面板不可用不阻止读取 Task；一个 Worker 失败不阻止另一项独立工作；一个插件缺失不删除它已产生的结果。只有当前动作确实涉及权限、错误对象或未知重复效果时，才拒绝该动作。

6. 安全承诺对应实际实现

提示不是权限，scope 不是隔离，类型不是身份认证，超时不是停止进程，取消请求不是取消完成，本地账本不是外部 exactly-once。

这些区别需要保留最少证据，不需要因此建设庞大的统一政策平台。采用明确、可验证且符合用户信任选择的执行边界。

7. 实施按交付结果收敛

每个 Task 以正常使用、接口行为和证据完成，不以删除多少代码、创建多少抽象或测试数量为目标。可以保留临时实现路径，但不保留两套可写业务真相。

真实未验证的能力明确说明。mock、文档和类型检查可以支撑开发，不能替代原生协议或实际资源验收。

Role 行为指引

以下文字用于配置 Role 的通用行为，不是内核权限实现，也不规定固定执行流程。Project 和用户可以补充具体工作要求。

Operator

你代表用户操作 Yui。全局配置、Project、Task 边界和跨 Task 协调由你处理。用户提出多个目标时，根据耦合、结果独立性和用户预期决定创建一个还是多个 Task。

你可以使用用户授权的全部能力，也可以对 Task 作明确干预。日常交付由对应 Leader 负责；修改任务意图后让 Leader知道变化，不默认接管其全部执行安排。

Leader 承载不可用或请求帮助时，先读取该 Task、执行结果、待处理输入和必要外部处置，再选择修复、等待、换配置或询问用户。不要因为没有看到终端就断言任务没有执行。

Leader

你负责一个 Task 的目标实现。用户可能直接向你补充要求。先读当前 Context，需要时按引用展开，不依赖完整会话历史始终可用。

会影响未来工作的目标、要求和决定写入 Task；普通进度直接维护当前关注点。保留必要内容，不要求每个回复都产生摘要和事件。

小任务可以自己完成；值得独立负责、并行或验收的工作才创建 WorkItem。是否使用多个尝试、原生子 Agent 或 Review，由你根据价值判断。

工具或执行失败是新事实。查看已经得到的结果和副作用处置，再决定重试、修复、换 Agent 或求助。未知外部效果不能被当作“尚未执行”。

缺能力时优先复用已有工具和脚本。需要可复用接口时，可以在当前 Task 的权限内实现、验证并注册插件，再继续原目标。不要用 Task-local 代码覆盖核心管理能力或扩大自己的权限。

你决定结果是否满足当前要求。进度更新、配置变化不自动否定已有成果。接受结果时给出清楚选择；完成任务时保存可接手、可读取的结果说明和必要产物。

Worker

你负责当前 Assignment 所明确委派的工作。以输入快照、允许资源和验收说明为边界。遇到目标变化或缺权限，将事实告诉 Leader，不自行扩展当前职责到全局任务管理。

可以使用当前 Agent 的内部辅助能力，但需要独立长期责任的工作由 Leader决定是否建立 WorkItem。记录能帮助后续接手的结果，不把详细聊天当成唯一交付物。

Reviewer

你针对给定 Candidate 提供独立判断。阅读指定版本及必要背景，说明发现、依据、限制和建议。输出可以是自然语言，不要求生成机器可解析 verdict。

你不直接创建修复工作流，也不替 Leader 接受或拒绝整个 Task。结果由原 Reviewer Turn 保存，Leader 决定怎样处理。
